# sieve-bench

## どのスタイライズドファクツが、シミュレーションを見破れるのか

**結論：よく報告される統計量ほど、識別力が低い。**

金融のエージェントベース・モデルや LLM シミュレーションの論文は、ほぼ必ず
「スタイライズドファクツを再現した」と書く。だがその再現が**何を証明しているか**は
測られてこなかった。ある統計量を再現できたことは、そのモデルが現実に近いことを
意味するのか。それとも、その統計量が誰にでも再現できるだけなのか。

ここではそれを直接測る。

## やり方

各統計量は、1本のリターン系列を1つの数に落とす。実データの窓を多数集めれば
その数の分布が出る。生成器の実行を多数集めれば、そちらの分布も出る。
**2つの分布がどれだけ重なるか**が、その統計量の識別力である。

重なりは AUC（ROC曲線下面積）で測り、表には

```
power = 2 |AUC - 0.5|      0 = 全く分けられない、1 = 完全に分かれる
```

を出す。**低い数字が、その統計量の弱点を名指ししている。**

比較対象には、正解が分かっている生成器を並べる。目的は落とすことではなく、
**落とせないことを見つけること**にある。

| 生成器 | 何を持っているか |
|---|---|
| `gaussian` | 何も持っていない。ここで分けられない統計量は使い物にならない |
| `student_t` | 重い裾。時間構造なし |
| `iid_bootstrap` | **周辺分布が実データと完全に同一。**時間構造だけが無い |
| `block_bootstrap` | 短期の時間構造のみ（ブロック長20） |
| `garch_norm` | クラスタリングを持つ標準的な計量経済モデル |
| `garch_t` | 上に加えて重い裾。**強い基準線** |

`iid_bootstrap` は特に重要である。周辺分布が実データそのものなので、
**これと分けられない統計量は「裾しか見ていない」ことの証明**になる。

## 結果

実データ：6指数（S&P500・日経225・FTSE100・DAX・ハンセン・EURO STOXX 50）の
日次対数リターン 36,079 点。長さ1000の窓を124本。
生成器は各200回。全統計量はスケール不変。

```

hill_right                     0.909      0.644     0.257      0.168       0.455     0.733
```

ここで意味があるのは桁であって、小数第3位ではない。

### 読み取れること

**1. ボラティリティ・クラスタリングの再現は、ほとんど何も証明していない。**

`acf_abs_1` は ABM 論文が最も頻繁に載せる統計量だが、`garch_norm` に対する識別力は
**0.075**、`block_bootstrap` に対して **0.089**。クラスタリングを何らかの形で持つ
生成器なら、ほぼ素通りする。「ボラティリティ・クラスタリングを再現した」という主張は、
**GARCH(1,1) と区別がつかないことを意味しているに過ぎない。**

**2. 合わせ込んだ量では判定できない。**

`ljung_box_sq` は `gaussian` / `student_t` / `iid_bootstrap` に対して 0.998〜0.999 と
ほぼ完璧に働くのに、`garch_norm` に対しては **0.090** に落ちる。GARCH は
まさにこの構造に合わせて作られたモデルだからである。

**これは分子動力学の力場検証と同じ話である。**密度に合わせ込んだ力場を密度で評価しても
何も分からない。判定は、**合わせ込んでいない量**でやらなければならない。

**3. 効いたのはレバレッジ効果だけだった。**

強い基準線 `garch_t` に対して power 0.85 以上を出したのは `leverage`（0.922）と
`aggregational_gaussianity`（0.869）、`excess_kurtosis`（0.852）。
`garch_norm` に対しては `leverage` の 0.967 が突出している。
GARCH(1,1) が対称なモデルであることの帰結である。

**そして `leverage` は、ABM 論文でほとんど報告されない。**

**4. 単独で全てを捉える統計量は存在しない。**

`block_bootstrap` を捉えられるのは `acf_abs_20`（0.883）と `acf_abs_decay`（0.879）だけ。
`garch_norm` を捉えられるのは `leverage`（0.967）だけ。
**両方を持たなければ、どちらかを見逃す。**単一のスコアではなくバッテリーが要る、
という主張の根拠がここにある。

**5. 「リターンは予測できない」は検証に使えない。**

`acf_return_1` は全生成器に対して 0.135〜0.355。誰でも再現できるので情報が無い。

## 再現

```bash
pip install -r requirements.txt
python3 fetch.py         # 指数データを取得（30秒ほど）
python3 run_power.py     # 6秒
```

**指数データは同梱していない。**Yahoo Finance の生レスポンスの再配布は
利用規約上グレーであり、それでベンチマークが消えるのは避けたい。
`fetch.py` が各自の手元に取得する。

取得期間は **絶対日付で固定** してある（2001-07-30 〜 2026-08-01）。
`range=25y` のような相対指定だと実行日によって窓がずれ、数字が再現しない。
取得した系列が上の表と同一かは `fetch.py` が SHA-256 で照合する。
照合に通れば、上の表がそのまま出る。

| 指数 | シンボル | 日数 | 期間 |
|---|---|---|---|
| FTSE 100 | `^FTSE` | 6,317 | 2001-07-30 〜 2026-07-31 |
| DAX | `^GDAXI` | 6,349 | 2001-07-30 〜 2026-07-31 |
| S&P 500 | `^GSPC` | 6,288 | 2001-07-30 〜 2026-07-31 |
| ハンセン | `^HSI` | 6,163 | 2001-07-30 〜 2026-07-31 |
| 日経225 | `^N225` | 6,122 | 2001-07-30 〜 2026-07-31 |
| EURO STOXX 50 | `^STOXX50E` | 4,846 | 2007-03-30 〜 2026-07-31 |

EURO STOXX 50 だけ開始が遅いのは、Yahoo にそれ以前が無いためである。

結果は `power.json` にも書き出される（AUC の生値も入っている）。

- `facts.py` — 統計量のバッテリー（13個）
- `generators.py` — 生成器と、実データからのパラメータ推定
- `run_power.py` — 識別力の測定
- `fetch.py` — データ取得とハッシュ照合

## 正直に書いておく限界

**この結果はまだ v0 であり、次の点で弱い。**

1. **LLM シミュレーションをまだ通していない。**今あるのは既知の生成器だけである。
   意味があるのは、公開されている LLM エージェント市場シミュレーションの
   出力を通した時点から
2. **実データの窓が重なっている**（窓1000・ストライド250）。124本は独立ではないので、
   AUC は依存標本上の値である。指数を跨いだ分だけ緩和されているが、解消はしていない
3. **Student-t の自由度推定が 2.65 と低すぎる。**標準化した集約リターンに
   `floc=0` で当てているため、極値に引かれている。`student_t` 生成器が
   捉えやすくなっている方向のバイアス
4. **GARCH は S&P500 のみで推定**し、それを全指数の基準線として使っている
5. **日次のみ。**日中データを入れると、マイクロ構造由来の統計量が追加できる
6. **統計量は13個。**Cont (2001) の主要な事実は覆っているが、網羅ではない
7. **`aggregational_gaussianity` が不安定。**データを 36,073 点から 36,079 点に
   変えた（各指数の先頭に1〜2日足しただけ）ところ、この統計量だけ
   `gaussian` 相手に 0.449 → 0.646、`garch_norm` 相手に 0.454 → 0.636、
   `block_bootstrap` 相手に 0.150 → 0.041 と動いた。他の12個は全て 0.085 以内。
   窓の切り出し位置がずれたことによるもので、**この統計量は現在の窓数では
   推定量の分散が大きすぎる。**窓を増やすか、定義を見直す必要がある

**2と3と7は次に直す。1が本番である。**

## 何のためにやっているか

生成的シミュレーションが企業や金融機関の意思決定に入り始めている一方で、
**その出力が現実と同じ形をしているかを、生成した側から独立に判定する手続きが
存在しない。**各社が自ら採点した妥当性スコアを公表している状態にある。

判定を作るには、まず**判定に使える統計量とそうでない統計量を分ける**必要がある。
この表はその最初の一枚である。
